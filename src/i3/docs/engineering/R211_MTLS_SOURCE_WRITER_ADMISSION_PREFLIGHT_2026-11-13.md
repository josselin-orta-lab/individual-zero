# I3 R2.11 preflight: source-bound writer admission over real loopback mTLS CAS

**Declared before implementation/tests on 13 November 2026.** Base `main` `cc3153fd6bc0b2711583b1d6c03c648a9270bba7`. Linked to [#1339](https://github.com/josselin-orta-lab/individual-zero/issues/1339), [#1331](https://github.com/josselin-orta-lab/individual-zero/issues/1331) and the [off-host release dependency](OFFHOST_M11_INDEPENDENCE_RELEASE_GATE_2026-11-13.md). This is a **test-only ingress integration** and not the actual independently operated M11.

## Testable missing capability

The existing `RemoteEngineeringWitness` CAS client can carry an operator-supplied validated TLS context (R2.10), but `serve_test_loopback` currently only serves plain HTTP on `127.0.0.1`. The test authority does not independently admit a TLS client principal or pin an allowed source release. HMAC possession alone cannot distinguish two certificate principals holding the same application key; the `source_sha256` in a birth claim is caller-supplied.

**Question:** can a *strict opt-in loopback TLS mode* accept only a specific mutual-TLS client certificate fingerprint **and** a separately configured exact source SHA on `register/verify/prepare/commit`, denying every other writer/source **before the authority applies any state transition**, while preserving the old deliberately HTTP-only test CLI and native protocol semantics?

**Precommitted falsifier:** any wrong same-CA client certificate + correct HMAC reaches `AuthorityStore.apply`; no client certificate passes; an authenticated but foreign source claim registers or consumes a nonce; a wrong server CA passes the client; a valid strict writer fails a normal no-World CAS register/prepare/commit/verify; an invalid partial mTLS configuration silently falls back to HTTP; or the change admits a scientific World / M11 independent GO.

## Bounded implementation and exact tests

- Add optional test-only `tls_context`, `expected_writer_cert_sha256` and `expected_source_sha256` to the **existing** `serve_test_loopback` constructor. All three must be present together for strict mode; reject mixed/partial settings, non-`SSLContext`, server context without `CERT_REQUIRED` or minimum TLS 1.2, and malformed explicit digest pins **before initializing any authority DB or listening socket**. Plain loopback defaults remain unchanged and are still test-only.
- In strict mode the TLS socket uses a server certificate and requests a verified client certificate. Immediately at `POST /v1/command`, compare the DER peer certificate's SHA-256 to the exact configured *writer pin* before reading or authorizing the HMAC request. After normal HMAC/canonical JSON validation, require a typed `claim.source_sha256` exactly equal to the separately configured *allowed source* before `AuthorityStore.apply`. No wildcard or fallback, no redirection and no credential in output. The caller retains native P1.3 authority; test ingress never chooses a motor.
- New isolated `tests/i3/test_engineering_remote_mtls_admission.py`: ephemeral CA and localhost server certificate, two independently issued same-CA writer certificates, foreign CA and source claims; **actual TLS handshakes** to `https://localhost:<ephemeral-port>` with `RemoteEngineeringWitness`. Prove allowed writer+source can register/verify/prepare/commit a no-World local engineering CAS receipt. Deny foreign same-CA writer despite valid HMAC, no writer cert, wrong trust CA and valid writer with wrong source; all denials precede DB registration or nonce consumption. Test fail-closed invalid constructor configs and preserve existing HTTP loopback regression. Do not create a new scientific source index or live World.

## Explicit missing authority and acceptance

This tests **authentication/admission software in one CI runner** only. The test CA, all temporary certificates, HMAC secret, server and SQLite remain under one test operator and one rollback domain. A certificate fingerprint is a configured admission control, **not** independent release/build attestation, per-life writer authorization, credential lifecycle, storage immutability or protected monotonic high-water. The CLI still provides plain HTTP on `127.0.0.1`; it must not be used as an off-host service. The old four-domain rollback counterexample is **still `FAIL_INDEPENDENT_M11`**. No operator-provisioned off-host B/C, HSM, WORM, disaster recovery, real mTLS deployment or source-build evidence is claimed.

Required CI: source-exact Python 3.11/3.12 I3 suite, engine/generation ownership and navigation checks; report PASS/REJECT/NOT_RUN and any discovered negative.
