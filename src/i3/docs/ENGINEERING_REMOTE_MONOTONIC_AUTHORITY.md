# I3 R2: remote monotonic engineering authority, protocol and trust boundary

**12 November 2026.** Engineering-only implementation for [issue #1331](https://github.com/josselin-orta-lab/individual-zero/issues/1331). Owner-selected development reference is I3 / P1.3 funded-v2. I1 stays the registered active engine; I3 Stage 2.1 scientific result remains `NOT_ISSUED`. No scientific cohort, World index or old-source admission is opened by this work.

## Testable claim

A separate **network-addressable monotonic CAS authority**, retaining its own SQLite high-water record across an application restart, can detect rollback of BOTH locally controlled I3 reservation and step-ledger files **provided the authority itself, its credentials and its persistent store are not rolled back or compromised**. A PREPARED CAS acknowledgement must be received before native `World.step`. A timeout, invalid response, stale head, conflicting writer or ambiguous local/remote phase stops the acting process rather than guesses about motor execution. A fresh process can reconstruct only a fully COMMITTED and verified local history.

The shipped reference service (`i3.lab.engineering_remote_authority`) binds to **127.0.0.1** for CI and test engineering. It is **not a deployed independent off-host authority**. A separate process is not the same as a separate trust domain. Host root, host disk snapshots, operator credentials, network control and server upgrades remain unproven. There is no M11 identity, active engine registration, external-world exactly-once action or general scientific survival claim.

## New surfaces

- `i3.runtime.engineering_remote_witness.RemoteEngineeringWitness`: strict JSON-over-HTTP CAS client. Requires HTTPS with normal TLS certificate verification except an **explicit opt-in to 127.0.0.1 HTTP in engineering tests**. Every request uses a fresh random nonce. A HMAC-SHA256 request signature authenticates the caller; a nonce-bound signed response authenticates the configured server **under the assumption the shared secret is protected**. Fixed 8 KiB input/output limits; finite timeouts; no redirects; no automatic request retry. The configured `authority_id` is an exact expected 64-character identifier.
- `i3.lab.engineering_remote_authority`: standard-library reference server with its **own** SQLite `I3RM` application ID, schema/authority identity and WAL/FULL-synchronous transactions. It holds one immutable genesis claim per life, and only CAS-transitions `COMMITTED(seq,head) -> PREPARED(seq+1, intent-digest) -> COMMITTED(seq+1,new-head,terminal)`. It never accepts a reset, duplicate preparation, conflicting head, late postmortem action or new action after the declared horizon. The server checks claim digest, not real source authentication or bodily physics. The CLI key argument contains only a **fixed test key** in CI and MUST NEVER be used with a production credential.
- `i3.runtime.engineering_step_ledger.REMOTE_MODE`: the exact remote mode is bound to the **genesis ledger hash**. Previous `UNANCHORED` and `SEPARATE_LOCAL_WITNESS_V1` engineering modes remain unchanged. There is no migration or silent mode fallback; a remote-bound ledger rejects reconstruction without the expected remote client.
- `NativeEngineeringSession`: an optional, strictly typed `remote_witness` parameter is exclusive with `witness_directory`. A new, already-independent engineering claim is still reserved **once** with existing I3 source/genome/world identity and simulated body.

## Native transaction ordering

1. Before any birth-like engineering process, validate current I3 source/genome/world, reserve the unique local engineering index, initialize a REMOTE_MODE genesis, then register the same genesis exactly once at the authority. A remote registration failure leaves the local slot **consumed and unusable**, never silently retries.
2. Before the next motor, verify the full local ledger and remote monotonic `seq/head/terminal`; verify in-memory Mind/World state. The native Mind alone chooses the next action from first-person `World.capture()` with its own finite `CognitiveBudget`.
3. Durably store the **local PREPARED intent**; then require an **authenticated REMOTE PREPARED acknowledgement** of the matching sequence, old head and intent digest **before** the new native `World.step` can execute.
4. Execute one native motor and prepaid learning, check E/V body settlement and death, seal local POST_PAID_LEARNING receipts. Submit remote COMMITTED with exact new ledger head and terminal. Only an authenticated COMMITTED acknowledgement permits the method to report a completed step.
5. On any exception or unknown remote response, the in-process session is permanently stopped. A fully sealed local and remote history may be checked anew and deterministically reconstructed in a new process, but a PREPARED or conflicting history is never advanced or reconstructed. Historical detached replay is owner-side verification, not a second lived motor or additional cognitive work granted to Mind.

## Evidentiary negatives and control cases

- Two local files, copied **together** to older mutually consistent versions, are detected if an independently running authority retains the later sequence. Existing separate-local-only witness demonstrably cannot reject that attack.
- Replay of a signed old HTTP response with a different request nonce, wrong HMAC key, foreign authority ID, non-HTTPS destination (outside explicit loopback), duplicate PREPARED/COMMITTED or stale CAS is not accepted.
- Concurrent writers cannot both receive PREPARED; remote outage prevents any unprepared new motor. Crash after remote PREPARED or after local seal but before remote COMMITTED remains **uncertain and closed**. Remote service restarts recover its own already-committed high-water record.
- A malicious actor capable of **restoring the remote authority database as well**, replacing/compromising both client and server signing credentials, modifying source code, or forcing external-world actions directly is **outside this reference model**. HMAC with a shared client/server secret does not prove independent server signing-key custody. No TPM, HSM, external log/witness quorum, protected off-host storage, trusted wall time, authenticated source release or production TLS endpoint is implemented.
- The server accepts client-provided head and declared terminal; it cannot itself verify actual native bodily calculations or real-world physics. The client and local ledger still perform such model-level checks. A compromised native caller can lie; the service is not an independent biology auditor.

## Verification and release

Focused isolated subprocess-backed tests cover initial registration, signed command/response, old local birth+ledger rollback, concurrent CAS, duplicate/terminal refusal, client/server key and authority mismatch, outage, pending motor, crash after seal, and process/service cold restart. Native tests exercise actual `Mind.decide -> World.step -> paid learning` in the **existing development fixture**, a separately running authority, an actual second Python interpreter and fail-closed crashes. Unit tests do not execute Stage-2 scientific cohort sources. Exact-source Python 3.11 and 3.12 CI are the acceptance gates; local checks alone cannot establish production correctness.

**Remaining R2 production/M11 gate:** deploy and independently administer a real remote authority on protected separate infrastructure, TLS with managed credentials not present in client code or command lines, immutable or hardware-backed external high-water attestation, authenticated source/writer custody, tested network partitions and catastrophic recovery, multi-host identity collision control, benchmark durable four-phase I/O and O(n²) chain reconstruction, and a separate auditable active-engine release. Passing the included loopback tests is **only a protocol feasibility milestone**, not an independent M11 GO.
