## Modèle de sécurité et limites (à publier avec toute conclusion)

La référence GitHub fait respecter une **allocation au plus une fois pour le workflow configuré** tant qu'elle existe. Ce n'est pas un verrou physique : administrateurs du dépôt, code exécuté hors CI ou suppression manuelle de références/release peuvent contourner la gouvernance. Ne jamais supprimer, mettre à jour ou recycler le ref de réservation, ni rejouer le job scientifique. Les environnements/GITHUB_TOKEN peuvent refuser `contents:write` : dans ce cas arrêt **avant exposition** ; ne pas assouplir les protections pendant le même protocole. Les artifacts Actions expirent (durée demandée : 90 jours, soumise à la limite du dépôt) ; la Release GitHub est **une conservation interne**, dont l'immutabilité doit être activée dans les paramètres du dépôt et vérifiée séparément. Sans configuration attestée, **ne pas déclarer de custodie externe indépendante ni d'archive indélébile**.

Le contrôle froid peut être **relancé en lecture seule sur les octets déjà archivés**, même après échec ; cela ne crée pas une nouvelle source scientifique. Les problèmes ultérieurs demandent un **autre préenregistrement et d'autres graines**, pas une réhabilitation de F1K a posteriori.

**Avant le tir, vérifier explicitement** : CI DEV_R complète sur même arbre PASS, accès GitHub `contents:write` uniquement pour la création du ref, référence de consommation absente, autorisation préalable ADR-0022, capacité d'archivage GitHub Release, aucun `K` exécuté en conception. Dans le cas contraire : **HOLD_NO_EXPOSURE**.
